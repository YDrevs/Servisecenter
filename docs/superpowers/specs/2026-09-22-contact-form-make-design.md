# Заявка з сайту → Make → ШІ → Calendar/Sheets/Telegram

Дата: 2026-09-22
Статус: спроєктовано, не реалізовано

## Контекст

Клієнт будує автоматизацію на Make.com із трьох незалежних частин:

1. **Vapi** — голосовий ШІ-агент, що приймає дзвінки в неробочий час і записує клієнта в Google Calendar.
2. **Заявка з сайту** → Make → сповіщення менеджеру в Telegram.
3. **Чат-віджет зі ШІ** на сайті, що відповідає клієнтам у реальному часі.

Частини 1 і 3 мають власні специфікації; **цей документ описує тільки частину 2** —
те, що стосується коду цього репозиторію.

Наявний стан: `POST /wp-json/leaderauto/v1/contact`
(`app/wp-content/plugins/leaderauto-core/includes/class-rest-contact.php`) валідує форму,
шле `wp_mail` і, якщо задані токен і chat ID, повідомлення напряму в Telegram Bot API.
**Заявка ніде не зберігається**: якщо обидва канали відмовили, дані клієнта втрачено.

## Рішення

| Тема | Рішення |
|---|---|
| Роль Make | Уся логіка після прийому заявки: ШІ-класифікація наміру, запис у Google Calendar або Sheets, повідомлення менеджеру. |
| Роль сайту | Прийняти форму, зберегти заявку, віддати її в Make одним HTTP-запитом. Про ШІ, календар і таблиці код не знає. |
| Напрямок зв'язку | Односторонній: сайт → Make. Make у сайт не стукає, тому публічний домен для цієї частини не потрібен. |
| Спосіб з'єднання | Варіант A: зберегти → надіслати одразу → запасний канал при невдачі. Черга (варіант B) і відправка з браузера (варіант C) відхилені. |
| Календар | ШІ **пропонує**, людина підтверджує. Автоматичний запис у робочий графік без підтвердження — ні. |
| Страховка | Заявка зберігається в базі сайту; прямий Telegram лишається запасним каналом; `wp_mail` лишається як є. |

Чому A, а не B: черга на WP-cron спрацьовує лише тоді, коли хтось відвідує сайт, тож
повтор міг би статися й через годину. Для потоку заявок СТО достатньо однієї спроби плюс
ручного повтору з адмінки.

Чому не C: URL вебхука був би видимий у коді сторінки, будь-хто зміг би слати в нього
сміття коштом ліміту операцій Make, і заявка ніде б не зберігалася.

## Потік

```
форма → POST /wp-json/leaderauto/v1/contact      (form.js не змінюється)
          │
          ├─ 1. валідація, honeypot, throttle     (є)
          ├─ 2. зберегти заявку → статус "new"    (нове)
          ├─ 3. POST у вебхук Make, таймаут 5 с   (нове)
          │      ├─ 200  → статус "sent"
          │      └─ інше → статус "failed" → прямий Telegram (є, стає умовним)
          ├─ 4. wp_mail                            (є, без змін)
          └─ 5. відповідь клієнту
                 ↓
              Make: фільтр за секретом
                    → ШІ визначає намір: тест-драйв | сервіс | консультація
                    → Google Calendar (подія «не підтверджено») або Google Sheets
                    → Telegram менеджеру
```

## Компоненти

Усе в плагіні `leaderauto-core`, за наявним стилем: один клас — одна задача.

| Файл | Відповідальність |
|---|---|
| `includes/class-leads.php` (новий) | Тип записів `leaderauto_lead`: реєстрація, збереження заявки, зміна статусу доставки, список і колонки в адмінці, дія «Надіслати ще раз». |
| `includes/class-make-dispatch.php` (новий) | Єдиний POST у вебхук Make: зібрати payload, додати заголовок із секретом, надіслати, повернути успіх/невдачу. Нічого не знає про REST і про адмінку. |
| `includes/class-rest-contact.php` (є) | Керує порядком кроків. `send_telegram()` викликається лише тоді, коли Make не прийняв. |
| `includes/class-settings.php`, `helpers.php` (є) | Два нові значення: URL вебхука й секрет. Правило те саме — змінна оточення важливіша за збережене в адмінці. |
| `leaderauto-core.php` (є) | Підключення нових класів. |

### Тип записів `leaderauto_lead`

Не публічний (`public => false`, `show_ui => true`), доступ `manage_options`, створення
вручну вимкнене. Власної сторінки на сайті не має, у пошук і мапу сайту не потрапляє.

| Дані | Джерело |
|---|---|
| ім'я, телефон, авто, повідомлення | форма |
| дата й час | момент відправки |
| статус доставки: `new` / `sent` / `failed` | результат кроку 3. `new` лишається, якщо URL вебхука не заданий, тобто інтеграцію вимкнено |
| сторінка, з якої надіслано | `Referer` запиту |

Колонки списку: дата, ім'я, телефон, авто, статус.

### Payload у Make

```json
{
  "event": "contact_form",
  "lead_id": 123,
  "name": "Іван",
  "phone": "+380950662921",
  "car": "BYD Song",
  "message": "Щось стукає в підвісці, хочу записатись",
  "created_at": "2026-09-22T14:30:00+03:00",
  "page_url": "https://…/contacts/"
}
```

`message` — текст, який у Make розбирає ШІ. `lead_id` дає менеджеру змогу зіставити рядок
у таблиці із заявкою в адмінці сайту.

### Захист вебхука

Спільний секрет у заголовку запиту; першим кроком сценарію Make — фільтр «далі тільки
якщо секрет збігся». Криптографічний підпис (HMAC) не беремо: у Make він потребує
зайвого модуля, а виграш для такого потоку заявок неістотний.

### Налаштування

Дві нові позиції поряд із наявними (`LEADERAUTO_CONTACT_EMAIL`, `LEADERAUTO_TELEGRAM_*`):

| Змінна оточення | Поле в адмінці |
|---|---|
| `LEADERAUTO_MAKE_WEBHOOK_URL` | URL вебхука Make |
| `LEADERAUTO_MAKE_SECRET` | Секрет вебхука |

Якщо URL порожній — крок 3 пропускається, і плагін поводиться точно як зараз. Це дає
можливість вмикати інтеграцію окремо на локальному й бойовому середовищах.

## Поведінка при збоях

| Ситуація | Що бачить клієнт |
|---|---|
| Збережено, Make прийняв | «Дякуємо! Ми зв'яжемось найближчим часом» (як зараз) |
| Make не відповів, Telegram спрацював | те саме |
| Збережено, жоден канал не спрацював | «Дякуємо» + «Якщо ми не передзвонимо сьогодні — наберіть нас: +380 (95) 066 29 21» |
| Не вдалося зберегти заявку | помилка (як зараз) |

Принцип: **помилку клієнт бачить лише тоді, коли ми справді втратили його дані.**
Невдачі доставки пишемо в `error_log`, як уже робить наявний код.

Кнопка «Надіслати ще раз» у рядка зі статусом `failed` — ручна заміна відхиленої черги.

## Сценарій у Make (поза репозиторієм)

Не код, але без цього частина не працює. Порядок модулів:

1. Custom webhook — приймає POST.
2. Фільтр за секретом.
3. ШІ-модуль: на вхід `message` + `car`, на вихід тип звернення
   (`test_drive` | `service` | `consultation`) і стислий переказ.
4. Розгалуження: `test_drive` / `service` → Google Calendar, подія зі статусом
   «не підтверджено»; `consultation` → рядок у Google Sheets.
5. Telegram — повідомлення менеджеру з типом звернення, контактом і посиланням на подію.

Часу запису у формі немає — ШІ бере його лише з вільного тексту, якщо клієнт його написав.
Тому подія створюється **як пропозиція**, а підтверджує її менеджер.

## Межі роботи

**Входить:** збереження заявок, відправка у Make, запасний Telegram, повтор з адмінки,
налаштування, ручна перевірка.

**Не входить:** Vapi, чат-віджет, фонова черга з повторами, автоочищення старих заявок,
поля дати/часу у формі, перевірка зайнятості слота, зворотний зв'язок Make → сайт,
заміна форми на Tally (обговорювалося, рішення відкладене).

## Ризики і відкриті питання

- **Персональні дані.** З цієї зміни телефони клієнтів зберігаються в базі сайту й
  потрапляють у резервні копії. Строк зберігання й автоочищення не закладені — це тема
  для окремого рішення.
- **Якість ШІ-класифікації** перевіряється лише на практиці. Три типи звернень легко
  плутаються, якщо клієнт пише коротко («потрібна консультація щодо сервісу»).
- **Ліміт операцій Make** на безкоштовному тарифі витрачається кожною заявкою, зокрема
  спамом, що пройшов honeypot. Фільтр за секретом відсікає лише сторонні запити, не спам
  через саму форму.
- **`wp_mail` на Railway** досі не перевірений — це окрема задача деплою.

## Ручна перевірка

Тестів у проєкті немає (`CLAUDE.md`), тому перевірка покрокова:

1. `make site`, відправити форму → заявка у списку зі статусом `sent`.
2. Неробочий URL вебхука → статус `failed`, у Telegram прийшло запасне повідомлення.
3. Кнопка «Надіслати ще раз» із правильним URL → статус змінився на `sent`.
4. Запит у вебхук без секрету → сценарій Make його відкинув.
5. Прогнати через сценарій 3–4 різні тексти («хочу подивитись Sea Lion», «стукає
   підвіска», «скільки коштує діагностика») → ШІ визначив тип правильно.

Пункти 1–3 перевіряються локально, 4–5 — у Make. Робота не вважається завершеною, поки
пункт 5 не прогнано вручну.
