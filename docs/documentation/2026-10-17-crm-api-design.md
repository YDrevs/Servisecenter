# API заявок для CRM — дизайн

Дата: 2026-10-17 · Статус: погоджено · Етап 3 з 3 (етапи 1–2 — `…-leads-admin-design.md`, `…-make-webhook-design.md`)

## Мета

Самописна CRM сама забирає заявки із сайту (інкрементально) і може змінювати їм статус
та нотатку. Дані клієнта змінює лише форма на сайті.

## Автентифікація

- Заголовок `X-Api-Key: <ключ>` у кожному запиті.
- Ключ: env `LEADERAUTO_CRM_API_KEY`, інакше поле **CRM API key** у Settings → LeaderAuto.
  Поле приймає лише ключ ≥ 32 символів (коротший → помилка налаштувань, ключ не змінюється).
- Порівняння — `hash_equals`.
- Ключ на сайті порожній → `503 leaderauto_api_disabled`; ключ відсутній / хибний → `401 leaderauto_api_unauthorized`.

## Ендпоінти — `/wp-json/leaderauto/v1`

### `GET /leads`

| Параметр | За замовчуванням | |
|---|---|---|
| `updated_since` | — | ISO 8601 (`2026-10-17T10:00:00+03:00`); заявки з `updated_at >= updated_since`. Невалідна дата → `400` |
| `status` | усі: `la_new,la_progress,la_done,la_cancel,trash` | список через кому з цих значень; інше → `400` |
| `page` | 1 | ≥ 1 |
| `per_page` | 50 | 1…100 |

Сортування: `updated_at` ↑, потім `id` ↑. Відповідь:

```json
{ "items": [ { …lead… } ], "page": 1, "per_page": 50, "total": 3, "total_pages": 1 }
```

### `GET /leads/{id}`

Одна заявка (включно з тими, що в кошику). Немає / не заявка → `404 leaderauto_lead_not_found`.

### `PATCH /leads/{id}`

Тіло JSON, хоча б одне поле:

| Поле | Правило |
|---|---|
| `status` | один з `la_new`, `la_progress`, `la_done`, `la_cancel`, інакше `422` |
| `note` | рядок ≤ 2000 символів (`sanitize_textarea_field`), інакше `422`; повністю замінює нотатку |

- Порожнє тіло → `400`. Заявка в кошику → `409 leaderauto_lead_trashed`.
- Спочатку пишеться нотатка, потім `wp_update_post` (оновлює `updated_at`; при зміні статусу —
  подія `lead.status_changed` у Make зі свіжою нотаткою).
- Відповідь `200` — оновлена заявка.

## Формат заявки

`Leads::to_array()` (той самий, що в Make) + нове поле `updated_at` (ISO 8601, `post_modified`).
`status` може бути `trash`; тоді `status_label` = «У кошику».

`updated_at` змінюється при: створенні, зміні статусу, збереженні картки в адмінці, `PATCH`,
переміщенні в кошик / з кошика. Остаточне видалення з кошика CRM не бачить.

## Синхронізація (рекомендація для CRM)

1. Перший запуск — без `updated_since`, гортати `page` до `total_pages`.
2. Запам'ятати найбільший `updated_at` з отриманих.
3. Далі — `updated_since=<він>` (межа включна → можливі повтори; CRM робить upsert за `id`).

## Перевірка (`curl`)

1. Без ключа → 401; хибний → 401; ключ на сайті порожній → 503.
2. `GET /leads` → усі заявки, сортування, пагінація (`per_page=1`).
3. `updated_since` → лише змінені після; невалідна дата → 400; поганий `status` → 400.
4. `PATCH` статус + нотатка → 200, `updated_at` зріс, у картці нові значення, Make отримав `lead.status_changed` з нотаткою.
5. `PATCH` поганий статус → 422; порожнє тіло → 400; неіснуючий id → 404; заявка в кошику → 409.
6. Заявка в кошику видна в `GET /leads` зі `status: "trash"`.
